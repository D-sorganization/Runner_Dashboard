# Versioned Releases, Artifact Verification, and Container Images

Part of the deployment and release hardening epic (#3727). This page answers
one question for an operator deciding what to trust: **what, exactly, does a
Runner Dashboard "release" verify, and does that cover container images?**

## The signed release artifact (what exists today)

The authoritative, versioned release is the tarball built by the `Release`
workflow (`.github/workflows/release.yml`) from `runner-dashboard/VERSION`,
on a tag push, manual dispatch, or a protected `main` push that bumps
`VERSION`. It is:

- **Cosign-signed** with keyless OIDC/sigstore signing.
- **Attested** with SLSA-3 build provenance via
  `actions/attest-build-provenance`.
- **Accompanied by an SBOM** (`sbom.spdx.json`) generated by
  `anchore/sbom-action` (syft).
- **Checksummed**, with the checksum published alongside the artifact.

Full detail on the artifact's contents, version source of truth, local
build, and install/rollback flow: [`docs/ARTIFACT_BUILD.md`](ARTIFACT_BUILD.md).

## Container images: CI validation only, not a published release artifact

`.github/workflows/docker-build.yml` builds a Docker image on every PR that
touches Docker-relevant paths and on every push to `main`, then runs a Trivy
vulnerability scan against it. That build:

- Tags the image `runner-dashboard:ci-<sha>` for the scan and discards it
  afterward — the image is **not published** to any registry. `release.yml`
  itself never pushes to a registry either; there is no `ghcr`, `docker
push`, or registry step anywhere in the release pipeline.
- Builds for a single platform (whatever `docker buildx build` defaults to
  on the runner) — it does not pass `--platform`, so there is no multi-arch
  (`linux/amd64` + `linux/arm64`) output.
- Gets none of the signed-artifact flow's verification: no cosign signature,
  no SLSA provenance attestation, and no SBOM are produced for the container
  image. Those only cover the tarball described above.

**In short: today's "release" is the signed, SBOM'd, attested tarball. The
container image is a CI-only build-and-scan step with no published,
versioned, multi-arch, verified equivalent.**

## Gap tracked by this issue

Issue [#3724](https://github.com/D-sorganization/Runner_Dashboard/issues/3724)
tracks closing that gap: a published, versioned, multi-arch (amd64 + arm64)
container image carrying the same artifact-verification guarantees
(signature, attestation, SBOM) as the existing tarball release. That
pipeline change is not implemented by this page — it is release/deploy
pipeline work, and Runner_Dashboard deploys and releases of any kind are on
hold (HOLD #2657) pending owner sign-off. This document only records the
current, real state so operators and future implementers start from an
accurate baseline rather than assuming container images already carry the
tarball's verification guarantees.
