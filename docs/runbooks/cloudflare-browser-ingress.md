# Cloudflare Browser Ingress Runbook

## Status and Activation Gate

This runbook describes a future, owner-only browser path for the Runner Dashboard. It does not authorize or enable public ingress. Do not create a tunnel, DNS route, Access application, service, or account setting until the complete ADR-0007 route split, browser session/CSRF protections, Cloudflare Access validator integration, owner check, rate limits, and SSE behavior have merged and passed acceptance tests. Keep the external ingress feature flag disabled until the evidence matrix below is complete. Do not change router forwarding or expose a listener beyond loopback.

The intended browser URL is `https://ops.d-sorganization.org`. The origin is `http://127.0.0.1:8321` on DeskComputer. Cloudflare Tunnel is an outbound connector that publishes a hostname-to-local-service mapping; it does not require an inbound router port forward. The local application must continue to bind only to loopback.

## Configuration Inputs

Collect and verify these values from the Cloudflare Zero Trust application and approved Dashboard deployment configuration. Do not guess them or put credentials in this runbook:

- Access application name: `Runner Dashboard Owner Browser`.
- Public hostname: `ops.d-sorganization.org`.
- Access team issuer: the exact HTTPS team origin shown by Cloudflare, in the form `https://<team-name>.cloudflareaccess.com`.
- Audience tag: the exact audience tag shown for this Access application.
- Identity selector: the single verified owner identity for the configured GitHub IdP. Do not use a broad email-domain allow rule. Dashboard OAuth must independently enforce the configured numeric `owner_github_id`.
- Tunnel UUID and credentials-file path: generated by the Cloudflare account setup and stored with restrictive file permissions on DeskComputer.

Configure the Access validator with the exact issuer and audience values through the deployment configuration mechanism. The issuer and audience are identifiers, not proof of an authenticated user. Never accept issuer, audience, JWKS URL, or key URLs from a request or token. Keep this browser origin separate from `DASHBOARD_PUBLIC_ORIGIN` and `GITHUB_OAUTH_CALLBACK_URL`, which remain the canonical tailnet/MagicDNS OAuth origin unless an explicit, reviewed OAuth change says otherwise. The UI external origin must not silently replace the OAuth callback origin.

## Cloudflare Tunnel Topology

After the activation gate passes, configure a named tunnel with one published application route:

```yaml
tunnel: <verified-tunnel-uuid>
credentials-file: /etc/cloudflared/<verified-tunnel-uuid>.json
ingress:
  - hostname: ops.d-sorganization.org
    service: http://127.0.0.1:8321
  - service: http_status:404
```

Keep the credentials file readable only by the dedicated `cloudflared` service identity. Configure the tunnel as an outbound-only service with a restart policy. Do not add wildcard hostnames, private-network routes, alternate services, catch-all proxying, or any binding to `0.0.0.0`. Do not create a router port forward. Before starting the service, verify local Dashboard health and confirm the listener is loopback-only. Validate ingress rules with `cloudflared tunnel ingress validate`; this checks syntax, not end-to-end Access enforcement.

## Access Application and Policy

Create a Cloudflare Access **Self-hosted** web application for the one hostname. Access applications deny by default; configure one explicit Allow policy whose identity selector matches only the verified owner identity. Do not add bypass rules, service-token access, broad organization/domain access, or public paths. Keep machine and agent bearer APIs outside the browser exception; the Dashboard perimeter must reject those credentials when an external ingress marker is present.

Enable an independent Access MFA policy for the owner browser application. Require the browser **Security key** WebAuthn authenticator and/or **Biometrics** platform WebAuthn authenticator, and set the MFA authentication duration to require a fresh MFA challenge on every Access login (`0m`). Verify this setting on the actual application or matching policy; a global default can be overridden. Confirm a successful login shows the expected WebAuthn challenge and login fails when the challenge is canceled or absent. Retain redacted evidence of the policy setting and corresponding Access authentication event, without storing a raw JWT or session cookie.

Do not treat a GitHub login or an arbitrary JWT `amr` claim as proof of a passkey. Cloudflare documents independent MFA separately from IdP-based MFA and lists the IdPs supported for IdP-based MFA; GitHub is not listed there. Only rely on MFA evidence the actual Access policy and event explicitly establish.

## Route and SSE Verification

Run this matrix only after all code gates have merged and the external-ingress feature flag remains disabled until the full matrix is ready. Use a fresh browser session and redact cookies, tokens, identity values, and source IPs from saved logs.

| Request path | Expected result |
| --- | --- |
| Owner opens `https://ops.d-sorganization.org` before Access login | Access challenge; no Dashboard content |
| Owner completes Access WebAuthn MFA but lacks valid Dashboard OAuth session | Dashboard OAuth login; protected data remains unavailable |
| Owner completes Access MFA and valid Dashboard OAuth | Only explicitly allowed human browser UI/read routes and chat streams succeed |
| Non-owner identity | Access denies; no Dashboard details |
| Missing, expired, or invalid Access assertion | Generic denial; no protected response |
| External request with an agent or machine bearer token | Generic 403; structured server-side denial audit, no credential details |
| Browser mutation without valid session-bound CSRF and exact external Origin | 403 |
| Public request to a machine/admin route | Denied; local/tailnet caller retains its separate authorization path |
| Request directly to DeskComputer from outside the host | No reachable origin; listener remains loopback-only |
| Allowed staff thread/panel SSE stream | `text/event-stream`, `X-Accel-Buffering: no`, `Cache-Control: no-cache, no-transform`; events arrive incrementally |

For SSE, observe at least two events with timestamps while the connection stays open. Compare the public hostname response with the loopback response and confirm the edge does not cache or buffer the stream. Verify Access still authenticates the stream and no bearer-token path has been added. If the deployed route contract does not yet permit the tested browser request, that is a failed gate; do not widen the route to make this runbook pass.

Record the deployed Dashboard commit SHA, tunnel status, exact route hostname/service, Access application name, policy identity selector, issuer origin, audience tag, MFA method/session duration, and test result. Keep the audience and issuer as deployment configuration values; do not paste authorization headers, cookies, tokens, or private source IPs into the handoff.

## Kill Switch and Rollback

The first response to unexpected route, Access-policy, OAuth-origin, or SSE behavior is to stop the `cloudflared` service on DeskComputer using its reviewed service manager command. Then disable the published application route and its DNS record in Cloudflare, verify `ops.d-sorganization.org` no longer reaches the origin, and confirm the Dashboard remains accessible only through the existing loopback/tailnet path. Preserve configuration and redacted logs for diagnosis; do not delete tunnel credentials as part of incident response.

For a planned rollback, disable the public hostname route first, stop the connector second, and verify direct-origin isolation last. Keep Access protection enabled while any hostname route exists. Do not substitute a temporary bypass policy or change the Dashboard listener to a public interface to restore access. Re-enable only after the same acceptance matrix passes on the reviewed deployed SHA.
