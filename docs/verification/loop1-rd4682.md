## 2. Mechanism

`StaffWatchdog._run_loop` records child PIDs only on wakes where the leader is still alive. If the sampler thread is starved (a 14-minute full suite on a loaded runner) from before the child exists until after the leader exits, the first wake sees a dead leader and an empty tracked set, takes the `elif leader_exited: break` branch and ends with `failure_class=None`. The test's 3 s deadline then expires. The offline replay drives the real `_run_loop` on a virtual clock with the recorded wake schedule:

| Case          | Run                                   | Wake schedule                             | Verdict                         |
| ------------- | ------------------------------------- | ----------------------------------------- | ------------------------------- |
| `rd4682`      | 45882374313                           | gap 0.10 s to 0.60 s spanning leader exit | fail, `failure_class=None`      |
| `calibration` | 45873459525 (PR #4680, same workflow) | even 0.05 s wakes                         | pass, `failure_class="stalled"` |

Both verdicts repeat identically (tested three times each) and need no real processes or sleeping.

## 4. Stop gate (issue #4683)

"Stop before implementing shadow mode if the #4682 failure cannot be reproduced from information available before the authoritative check finishes."

Result: the failure reproduces offline only when given the wake schedule, which is observable after the run. Every pre-check feature (tree equals green PR head, workflow blob, diff does not touch the watchdog, PR checks green) is identical for the failing and passing cases, so a pre-check cannot tell them apart. `evaluate_stop_gate` returns `STOP_BEFORE_SHADOW`.

Consequence for #4684: a `--queue-advisory` predictor cannot honestly predict this class from the tree. It can only abstain (`unknown`) or flag known timing-sensitive tests. Needs an owner or Barb decision before shadow mode is built.
